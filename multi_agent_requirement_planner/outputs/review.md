# 多 Agent 需求评审材料

## 1. 需求分析

**核心目标**  
将模糊或半结构化需求转化为可评审、可执行的技术方案材料。

**目标用户**
- 产品经理
- 研发负责人
- 后端/前端工程师
- 测试或质量保障同学

**核心痛点**
- 需求描述分散，评审前需要反复补齐背景、边界和验收标准。
- 技术方案、风险评估和测试计划经常由不同角色重复整理。
- AI 输出缺少人工审核节点时，容易产生不可控变更风险。

**明确需求**
- 输入一段中文需求描述。
- 输出需求澄清问题、接口设计草案、实现拆分、风险点、测试建议和评审摘要。
- 支持人工审核，禁止 AI 直接合入代码或修改线上配置。

**待澄清问题**
- 输出评审材料是否需要固定模板或接入现有文档系统？
- 是否需要保存历史版本和评审意见？
- 是否需要连接 Jira、飞书、Slack、GitHub 或内部知识库？

## 2. 技术方案

采用多 Agent 串行工作流：需求解析、技术方案、风险评估、测试规划、文档汇总。

## 3. 风险评估

- 模型可能遗漏项目特定约束。
- 需求描述过短时，生成方案可能过度假设。
- 敏感信息需要脱敏或禁止发送给外部模型。

## 4. 测试计划

- 验证空输入会被拒绝。
- 验证 Markdown 和 JSON 均能正常生成。
- 验证系统默认不执行自动合入或线上变更。

## 5. 评审结论

该方案适合作为研发提效 PoC：它不直接替代人工决策，而是把需求解析、方案草案、风险识别和测试规划前置自动化，并通过人工审核节点控制交付风险。
